---
title: "Account Validation"
description: "Check a recipient exists — and that it belongs to who you think — before you send them money."
---

Paying the wrong account is expensive and usually irreversible. Account
validation lets you check a destination before you commit to it.

There are two levels, and which you get depends on your account:

| | Available to | Tells you |
| --- | --- | --- |
| **Format & corridor check** | Everyone | Whether the number is well formed and the corridor is supported |
| **Name resolution** | Accounts enabled for name lookup | Who the account actually belongs to, and whether that matches who you expected |

Both come from the same endpoints, with the same request shape. Without the
entitlement you get the format check and `nameLookupStatus: "NOT_ENABLED"`;
with it, the response gains `accountName`, `accountStatus` and — if you asked
for it — `nameMatch`.

## Validating a phone number

<CodeGroup>
```bash Request
curl -X POST https://api.kotanipay.com/api/v3/customer/validate/mobile-money \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "phoneNumber": "+254712345678" }'
```

```json Response
{
  "isValid": true,
  "isSupported": true,
  "countryCode": "KE",
  "currency": "KES",
  "internationalNumber": "+254712345678",
  "network": "MPESA",
  "mno": "SAFARICOM KENYA",
  "accountName": "JANE MARY DOE",
  "nameLookupStatus": "MATCHED"
}
```
</CodeGroup>

You don't need to tell us the mobile network — it's resolved from the number's
prefix, and returned as `network` (the rail the lookup used) and `mno` (the
operator the number belongs to). Send `network` yourself only if the number has
been ported, or if a response says the network couldn't be determined.

## Which field answers which question

Three fields look similar and answer different questions. Read them together:

| Field | Question it answers |
| --- | --- |
| `isSupported` | Do we serve this country and rail at all? |
| `isValid` | Is this a usable destination? |
| `nameLookupStatus` | Did we manage to resolve the name on it, and what came back? |
| `nameMatch.matched` | Is the holder the person you named in `accountName`? |

`isValid` starts from the account number or phone number format, and is
**overridden to `false`** when a lookup comes back `NOT_FOUND` — at that point we
have asked and the account does not exist, which is stronger evidence than any
format check. For every other status (`ERROR`, `TIMEOUT`, `UNSUPPORTED`,
`NOT_ENABLED`) we could not find out, so `isValid` keeps reporting the format
result and you should read `nameLookupStatus` to see why.

<Warning>
A name mismatch does **not** make `isValid` false. `isValid: true` with
`nameMatch.matched: false` means the account is real but belongs to somebody
other than the name you sent — which is usually the more urgent problem. Check
both before paying out.
</Warning>

## When a lookup doesn't return a name

`nameLookupStatus` is always accompanied by `nameLookupReason` explaining it, so
you can tell the cases apart rather than retrying blindly:

| Status | What it means | Retrying helps? |
| --- | --- | --- |
| `MATCHED` | Name resolved | — |
| `NOT_FOUND` | The network or bank confirmed there is no such account, shortcode or subscriber. Also sets `isValid` to `false` | No — check the number |
| `UNSUPPORTED` | This corridor can't resolve names, or we couldn't determine the network | No |
| `TIMEOUT` | The network didn't answer in time | Yes |
| `ERROR` | The check didn't complete. Usually the network being busy or briefly unavailable rather than anything wrong with the account — `nameLookupReason` has the specifics | Yes, after a short wait |
| `NOT_ENABLED` | Your account isn't enabled for name lookup | No |

The distinction that matters is `NOT_FOUND` versus `ERROR`. `NOT_FOUND` is an
answer — the account isn't there, and asking again won't change that. `ERROR`
means we never got an answer, so the account may well be fine. Read
`nameLookupReason` rather than the status alone; it carries the network's own
wording, such as `"System is busy, please retry later"`.

## Validating a bank account

Send the account number, the bank code and the country.

```json
{
  "accountNumber": "1234567890",
  "bankCode": "68",
  "countryCode": "KE"
}
```

Alongside the name, bank responses carry `accountStatus` — `ACTIVE`, `FROZEN`
or `RESTRICTED`. A frozen or restricted account will usually reject an incoming
payment, so it's worth checking before you send.

## Paybill and till

Set `accountType` to `paybill` or `till` and send `shortCode` instead of
`phoneNumber`. For a paybill you can also pass `accountReference` — the value a
payer would enter as the account number.

```json
{
  "accountType": "paybill",
  "shortCode": "247247",
  "accountReference": "0123456789"
}
```

A shortcode is just digits, so there's no useful format check for one — whether
it exists is exactly what the lookup answers. These two types therefore need
name lookup enabled.

## Confirming the recipient is who you expect

Send `accountName` with the name you're expecting and the response adds a
`nameMatch` block.

```json
{
  "accountNumber": "1234567890",
  "bankCode": "68",
  "countryCode": "KE",
  "accountName": "Jane Doe"
}
```

```json
{
  "accountName": "JANE MARY DOE",
  "nameMatch": {
    "provided": "Jane Doe",
    "score": 100,
    "matched": true,
    "threshold": 70,
    "masked": false
  }
}
```

Names are compared token by token rather than as exact strings, because real
account names rarely come back in the format you sent them. `Jane M Doe`,
`Doe Jane Mary` and `Jane Mary Doe` all match `JANE MARY DOE`; `Robert Doe`
does not.

<Warning>
When `masked` is `true` the provider only returned part of the name, so the
match is based on the visible portion alone. Treat that as "not contradicted"
rather than confirmed.
</Warning>

## Blocking payouts on a name mismatch

If you'd rather not check every recipient yourself, we can enforce it for you:
your bank payouts get name-checked before dispatch, and any payout whose
recipient name doesn't match is failed instead of sent.

This is off by default and configured per account, including how close the match
has to be. Talk to your account manager if you want it enabled.
