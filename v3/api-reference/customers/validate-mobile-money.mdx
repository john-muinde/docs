---
title: "Validate Mobile Money Account"
openapi: "POST /api/v3/customer/validate/mobile-money"
---

Checks a recipient before you pay them: the number format, the country it
belongs to, and whether that corridor is supported.

## What to send

Which fields are required depends on `accountType`, so the schema below marks
them all optional. In practice there are two shapes:

<CodeGroup>
```json Phone number
{
  "phoneNumber": "+254712345678"
}
```

```json Local number
{
  "phoneNumber": "0712345678",
  "countryCode": "KE"
}
```

```json Paybill or till
{
  "accountType": "paybill",
  "shortCode": "247247"
}
```
</CodeGroup>

| Sending | Required | Also accepted |
| --- | --- | --- |
| A phone number (default) | `phoneNumber` in international format, **or** `phoneNumber` + `countryCode` | `network`, `accountName` |
| A paybill or till | `accountType`, `shortCode` | `accountReference` (paybill only), `countryCode`, `accountName` |

Send the number in international format (`+254712345678`) or supply
`countryCode` alongside a local one. A local number on its own is genuinely
ambiguous — `0712345678` is a real number in seven of the countries we support
— so rather than guess, the response asks you which country you mean.
`countryCode` defaults to `KE` for a shortcode.

You do not need to send `network`. It is resolved from the number's own prefix,
and the response tells you which network was used (`network`) and which operator
the number belongs to (`mno`). Send it only if the number has been ported, or if
a response tells you the network could not be determined.

## Resolving the account holder

If your account is enabled for **name lookup**, the response also carries the
name registered on the number (`accountName`) and `nameLookupStatus`. Without
that entitlement you still get the format and corridor checks, and
`nameLookupStatus` comes back as `NOT_ENABLED` — the request is identical
either way.

Whenever a lookup does not return a name, `nameLookupReason` says why, so you
can tell a number that does not exist (`NOT_FOUND`) from a corridor that cannot
resolve names at all (`UNSUPPORTED`) from something that needs a retry
(`ERROR`, `TIMEOUT`). Check `nameLookupReason` before retrying — `UNSUPPORTED`
will not resolve on a second attempt.

Send `accountName` with the name you expect and the response adds a `nameMatch`
block scoring it against the real one, so you can catch a wrong number before
the money moves.

## Paybill and till

A shortcode is just digits, so there is no useful format check for one — whether
it exists is exactly what the lookup answers. These two types therefore need
name lookup enabled, and `accountReference` is the value a payer would enter as
the account number on a paybill.
